# Postman collection

Thirty requests covering the PepperX REST API, grouped by concern. Every request carries a
description explaining not just what it does but the behavior worth knowing — why object keys are a
query parameter, why deletes wait, why `null` and `ClearObject` mean different things.

## Import

1. Postman → **Import** → select both files:
   - `PepperX.postman_collection.json`
   - `PepperX.postman_environment.json`
2. Select the **PepperX (local)** environment.
3. Run **Health → Server info** to confirm the endpoint is a PepperX node.

## Variables

| Variable | Default | Notes |
|---|---|---|
| `baseUrl` | `http://localhost:8000` | The node's REST endpoint |
| `container` | `telemetry` | Container used throughout the collection |
| `objectKey` | `metrics/cpu.json` | Object key. URL-encode reserved characters. |
| `requestId` | *(empty)* | A request-history record ID, from the list endpoint |
| `s3BaseUrl` | `http://localhost:8001` | The node's S3 endpoint (S3 folder) |
| `uploadId` | *(empty)* | S3 multipart UploadId, captured automatically by **S3 → Multipart → Create multipart upload** |
| `part1Etag` | *(empty)* | An S3 part ETag to paste into the S3 Complete request body |
| `restUploadId` | *(empty)* | REST multipart UploadId, captured automatically by **REST → Multipart → Initiate multipart upload** |
| `restPart1Etag` | *(empty)* | A REST part ETag to paste into the REST Complete request body |

## Running it top to bottom

The folders are ordered so a full run works: Health, Containers, Objects, Search, Admin, Request
history, then Cleanup. The destructive deletes live in **Cleanup** at the end rather than in their
own folders, so running the collection straight through does not delete the container that later
folders depend on.

The **REST → Multipart** subfolder covers the native REST multipart lifecycle (`{{baseUrl}}`): **Initiate
multipart upload** captures the `UploadId` into `restUploadId`, then Upload part, Upload part (copy),
List parts, Complete, List in-progress, and Abort reuse it. Save each Upload part response ETag into
`restPart1Etag` (etc.) before sending Complete.

The **S3** folder mirrors the S3-compatible surface (`{{s3BaseUrl}}`). Its **Multipart** subfolder
runs the same way with the `uploadId`/`part1Etag` variables.

With [newman](https://github.com/postmanlabs/newman):

```bash
npx newman run postman/PepperX.postman_collection.json \
  --env-var baseUrl=http://localhost:8000 \
  --env-var container=scratch \
  --env-var objectKey=metrics/cpu.json
```

Use a throwaway `container` value. The run creates it, writes to it, and deletes it — pointing it at
a container you care about will destroy that container's contents.

## A warning worth repeating

PepperX has no authentication. Every request in this collection works against any node you can reach,
including the ones marked DESTRUCTIVE. There is no confirmation step and no undo.

## Staying current

The live contract is always `{{baseUrl}}/openapi.json`, with Swagger UI at `{{baseUrl}}/swagger`. If
this collection and the OpenAPI document ever disagree, the document is authoritative — it is
generated by the server from the same route definitions it serves.
